## 1. 产品概述

### 1.1 产品定位
面向**胸痛中心（专病质控）**的业务协同与管理平台。支撑从患者就诊建档、标准化填报、三级审核、质控统计，到出院随访、远程心电协同、三会（例会/质量分析会/典型病例讨论）与继续教育的全流程数字化。

### 1.2 建设目标
| 目标 | 说明 |
|---|---|
| 标准化填报 | 用统一字段字典（67 个标准字段）规范胸痛病例数据采集，保证跨院区可比 |
| 流程闭环 | 建档 → 填报 → 审核 → 质控 → 随访形成可追溯闭环 |
| 协同提效 | 远程心电会诊、AI 识别填报、知识库问答降低医生事务性负担 |
| 质控可视 | 数据统计模块输出质控指标，支撑胸痛中心认证与持续改进 |

### 1.3 产品范围
- **包含**：三端协同的核心业务（建档/填报/审核/模板/随访/远程心电/三会/学院/公告/增值服务/数据统计/业务日志）+ 业务侧账号体系。
- **不包含（外系统/非本期）**：框架级系统基座（RBAC/存储/定时任务/代码生成，由后端 `module_system` 提供，本期不纳入产品需求）、独立「患者主索引」表（当前患者信息存于病例表）、邮件通知（无 SMTP 实现）、第三方 OAuth 登录（鉴权为自研 JWT）。

### 1.4 术语
| 术语 | 含义 |
|---|---|
| 病例（case_record） | 一次就诊事件的聚合记录，系统主表 |
| 填报明细（case_detail） | 按模板填写的一张表单内容 |
| 填报模板（report_template） | 定义表单结构（字段、顺序）的配置 |
| 三级审核 | 病例经多角色逐级审核的质控流程 |
| 合诊患者 | 远程心电发起后关联到病例的患者（`ecg_consult.case_id` 非空） |

## 2. 用户角色与权限

系统采用**业务侧 RBAC**，角色码与中文名（代码实测）：

| 角色码 | 中文名 | 核心职责 | 典型权限边界 |
|---|---|---|---|
| `admin` | 管理员 | 医院/科室/医生账号管理、全局配置 | 可管理医生账号、查看全量数据 |
| `auditor` | 审核员 | 病例三级审核、质控把关 | 评审病例、写审核结论 |
| `doctor` | 医生 | 建档、填报、随访、心电、AI 辅助 | 仅操作本人/授权范围内的病例 |

> 权限校验机制：`BusinessRole([ROLE_ADMIN])` 等装饰器做接口级校验（见 `auth/dependencies.py`）。登录态基于自研 JWT。

## 4. 详细功能需求

### 4.1 业务认证（auth）— P0
| 编号 | 功能 | 描述 | 验收标准 |
|---|---|---|---|
| F-AUTH-01 | 业务登录 | `POST /cpx/auth/login` 手机号/账号+密码换取 JWT | 返回 token；错误凭证返回明确错误 |
| F-AUTH-02 | 业务登出 | `POST /cpx/auth/logout` | 失效当前会话 |
| F-AUTH-03 | 当前用户信息 | `GET /cpx/auth/userinfo` | 返回角色码、姓名、医院等上下文 |

### 4.2 医生端主流程（doctor）— P0
| 编号 | 功能 | 描述 | 验收标准 |
|---|---|---|---|
| F-DOC-01 | 建档 | 创建病例主记录（患者姓名、医院、接诊医生、就诊时间） | 生成 `case_no`；落 `case_record` |
| F-DOC-02 | 保存填报 | `save_form` 按模板存 `case_detail.form_data` | 草稿可暂存，不触发审核 |
| F-DOC-03 | 提交审核 | `submit` 进入审核流 | 状态变更；审核员可见 |
| F-DOC-04 | 病例列表/详情 | 我的病例分页查询与详情 | 字段与 `fields.py` 字典一致 |
| F-DOC-05 | 随访计划生成 | `POST /followup/generate` 审核通过后生成 1/3/6/12 月计划 | 自动生成随访单 |
| F-DOC-06 | 随访提交 | `POST /followup/{id}/submit` | 表单落库，关联病例 |

### 4.3 AI 辅助能力（doctor）— P1
| 编号 | 功能 | 真实接口 | 描述 | 验收标准 |
|---|---|---|---|---|
| F-AI-01 | 图片/文字识别填报 | `POST /ai/recognize` | 识别就诊资料提取患者信息 | 返回结构化字段，可回填表单 |
| F-AI-02 | 语音识别 | `POST /ai/asr` | 音频转写（智谱 GLM-ASR） | 返回文本 |
| F-AI-03 | 远程心电上传与诊断 | `POST /ecg/upload` | 上传心电图 + AI 诊断 + 病例快照 | 生成 `ecg_consult` 记录 |
| F-AI-04 | 心电协同会诊 | `POST /ecg/send-consult/{id}` + `/ecg/feedback/{id}` | 发起/接收方反馈 | 会诊状态流转完整 |
| F-AI-05 | 认证知识库问答 | `POST /kb/ask` | 基于认证资料问答，标注来源文件与页码 | 返回答案+来源 |
| F-AI-06 | AI 再认证自评 | `GET /selfcheck` | 模拟再认证自评 | 返回评分/建议 |

## 5. 核心业务流程

### 5.1 主流程：建档 → 填报 → 审核 → 随访
```
医生建档(case_record) → 保存填报(case_detail,草稿) → 提交(submit)
   → 审核员三级审核(audit_record) → 通过 → 生成随访计划(follow_up)
   → 医生按期提交随访 → 闭环
```

### 5.2 远程心电协同
```
医生上传心电图(ecg/upload, AI 诊断) → 可选发起协同会诊(send-consult)
   → 接收方反馈(feedback) → 会诊结束（可关联病例）
```

### 5.3 AI 填报辅助
```
上传图片/语音 → recognize/asr 提取结构化信息 → 回填表单 → 医生确认 → 提交
```

## 6. 数据需求（核心实体）

主表 `case_record`；其余事件表均经 `case_id` 外键挂载：

| 实体 | 表 | 关系 |
|---|---|---|
| 病例 | case_record | 主干，存患者姓名等 |
| 填报明细 | case_detail | 1:N 挂 case_record；引用 report_template |
| 审核记录 | audit_record | 1:N 挂 case_record |
| 随访 | follow_up | 1:N 挂 case_record |
| 远程心电 | ecg_consult | 1:N 挂 case_record（case_id 可空） |
| 模板 | report_template | 被 case_detail 引用 |

> 字段标准源：`backend/app/plugin/module_cpx/fields.py`（67 个标准字段字典），Web 与 App 表单均由此驱动。

## 7. 非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | 列表分页；AI 接口异步调用外部模型，需超时与降级 |
| 安全 | JWT 鉴权；接口级角色校验；患者 PII 敏感字段加密存储 |
| 兼容 | Web 现代浏览器；App 支持 H5/小程序，含定位与地图（高德） |
| 可用性 | 字段字典驱动，新增采集项无需改两端代码 |
| 部署 | 支持 Docker 容器化（mysql/redis/backend/web 四服务） |

## 8. 接口需求

- 风格：RESTful，前缀 `/api/v1/cpx/*`；JSON 收发。
- 统一响应：后端 `common` 封装响应体。
- AI 接口：见 4.3，需标注模型来源与失败处理。
- 文档：Swagger 在 `localhost:8002/api/v1/docs` 自动生成，作为接口契约。

## 10. 剔除声明（避免虚构）

| 不包含项 | 原因 |
|---|---|
| 独立「患者主索引」表 | 患者信息存于 case_record，无 patient 表 |
| SMTP 邮件通知 | 依赖中无邮件发送实现 |
| 第三方 OAuth 登录 | 鉴权为自研 JWT |
| DataMAX 大屏为系统组成 | 它是云端外部服务，不在本仓库代码内 |
| 通用 AI 对话（module_ai/chat） | 孤儿功能，无页面入口，不计入在用需求 |
