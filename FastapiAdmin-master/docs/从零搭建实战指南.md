# 从零搭建实战指南（小白详细版）

> 适用：你是个新手，想从零做一个「**后端 API + 管理端网页 + 手机 App**」三端协同的业务系统。
> 本指南以当前仓库（FastapiAdmin 改造的胸痛中心系统）为**真实样板**，所有命令、文件、代码都来自本仓库已验证的内容，可以直接照抄。
> 配套文档：`docs/学习路线.md`（怎么读这个项目）、`docs/开发环境配置清单.md`（环境细节）、`docs/数据模型ER图与API接口设计.md`（表结构）。

---

## 第 0 章 · 先弄懂几个词（不懂后面全懵）

用「餐厅」打比方：

| 词 | 大白话 | 本项目对应 |
|---|---|---|
| **后端 Backend** | 餐厅后厨：接单、做菜、存原料 | `backend/` 文件夹，FastAPI，端口 **8002** |
| **前端 Frontend** | 顾客看到的菜单 + 点餐员 | 网页 `frontend/web/`（端口 5180）、手机 `frontend/app/`（端口 5190） |
| **API** | 后厨和前厅之间的「传菜窗口」：前端按约定格式喊一声，后端回数据 | 比如 `POST /cpx/doctor/case/create`（"建个病例"） |
| **数据库 Database** | 仓库/账本，把数据永久存好 | MySQL 8.0（库名 `fastapiadmin`） |
| **ORM** | 不用写 SQL 也能操作数据库（用 Python 类当表用） | SQLAlchemy（`models.py` 里每个类 = 一张表） |
| **路由 Router** | 后厨里不同的窗口：`/doctor` 窗口专接医生单 | `controller.py` 里的 `APIRouter` |
| **虚拟环境 venv** | 给这个项目单独准备的工具箱，不污染电脑全局 Python | `backend/.venv/` |
| **端口 Port** | 电脑上的「门牌号」 | 8002 后厨门 / 5180 网页门 / 5190 App 门 |
| **Schema** | 规定"这个请求里必须带哪些字段、什么类型" | `schema.py` 里的 Pydantic 类 |
| **Service** | 真正干活的代码（连数据库、算结果） | `service.py` |

> 一句话记住整体：**前端在 5180/5190 喊 API → 后端 8002 接单 → service 干活 → 存进 MySQL → 把结果原路返回前端。**

## 第 3 章 · 后端骨架：让"后厨"开张

本项目后端**第一个该读的文件**是 `backend/main.py`（126 行）。它只有一个 `create_app()` 工厂函数，讲清"应用由什么组成"：异常处理 → 中间件 → 路由注册 → 静态文件 → 文档。

### 3.1 应用工厂（你照着写的最小骨架）

`backend/main.py` 的核心思路（不是抄全部，是理解结构）：

```python
# main.py（骨架示意，真实文件更全）
from fastapi import FastAPI
from app.core.discover import register_routers   # 动态挂所有业务模块

def create_app():
    app = FastAPI(title="我的系统")
    register_routers(app)        # ← 灵魂：自动把所有 module_*/controller.py 挂上来
    return app
```

### 3.2 本项目最值钱的设计：动态路由（重点理解）

文件 `backend/app/core/discover.py`。它干的事（已实测）：

1. 规定：业务代码放 `app/plugin/` 下，**文件夹名以 `module_` 开头**（如 `module_cpx`）。
2. 每个业务模块的控制器**必须叫 `controller.py`**。
3. 它用 `base_dir.glob("module_*/**/controller.py")` 扫描所有控制器文件。
4. 把 `module_xxx` 自动变成网址前缀 **`/xxx`**（去掉 `module_` 前缀）。

**效果（新手最该记住的一点）**：你以后新增一个业务模块，只要在 `app/plugin/module_新名字/` 下建 `controller.py`，**不用写任何"注册路由"的代码**，启动就自动生效。本项目里 `module_cpx` → 网址前缀 `/cpx`，所以医生端接口是 `/cpx/doctor/...`。

## 第 4 章 · 配置与启动（这里有大坑）

### 4.1 配置放哪

所有配置从 `backend/env/.env.{ENVIRONMENT}` 读（本项目用 pydantic-settings）。模板在 `backend/env/.env.example`，关键项：

```
ENVIRONMENT = dev          # 环境：dev 开发 / prod 生产
SERVER_PORT = 8001         # 注意：实际开发运行端口是 8002（见部署脚本/文档）
DATABASE_PORT = 3306
REDIS_HOST = localhost
REDIS_PORT = 6379
```

> 你做自己项目：数据库地址、Redis、密钥、第三方 API Key **全放 env 文件**，别写死在代码里。

### 4.2 启动后端（⚠️ 必看，本项目最大坑）

```bash
cd backend
ENVIRONMENT=dev ./.venv/Scripts/python.exe -m uvicorn main:create_app --host 0.0.0.0 --port 8002 --factory
```

> ⚠️ **必须带 `ENVIRONMENT=dev`**！不带的话，`setting.py` 会去找 `.env.None` 这个不存在的文件，数据库密码读到空 → 报 `Access denied (using password: NO)`。这是本项目新人必踩的坑。
>
> ⚠️ **不要加 `--reload`**：本项目改了 `service.py` / `controller.py` 后必须**手动重启**这个进程，否则跑的是旧代码（曾出现过"改了像没改"的灵异事件）。

启动成功标志：浏览器打开 `http://localhost:8002/api/v1/docs` 能看到 Swagger 在线文档页面。

## 第 5 章 · 数据层：先把"账本"建好

### 5.1 用 ORM 定义表（抄 `models.py` 的思路）

本项目业务表在 `backend/app/plugin/module_cpx/models.py`。真实表和外键（实测）：

```python
class CaseRecordModel(MappedBase):        # 表名 → case_record（一次就诊）
    __tablename__ = "case_record"
    hospital_id = mapped_column(ForeignKey("hospital.id"))   # 哪家医院
    doctor_id   = mapped_column(ForeignKey("user_account.id"))  # 哪位医生

class CaseDetailModel(MappedBase):         # 表名 → case_detail（填的一张表）
    __tablename__ = "case_detail"
    case_id     = mapped_column(ForeignKey("case_record.id"))   # 属于哪个病例
    template_id = mapped_column(ForeignKey("report_template.id")) # 用的哪个模板

class AuditRecordModel(MappedBase):        # 表名 → audit_record（一次审核）
    __tablename__ = "audit_record"
    case_id = mapped_column(ForeignKey("case_record.id"))
```

**你照做**：先画 ER 图（见 `docs/数据模型ER图与API接口设计.md`），再用 `Mapped` / `mapped_column` 把每个类写出来。外键就是你图里连的线。

> 核心表关系一句记住：**`case_record` 是一次就诊的主表，填报明细、审核、随访、远程心电都靠 `case_id` 挂在它下面**（都是围绕这次就诊发生的"事件"）。

### 5.2 灌种子数据

本项目 `backend/app/scripts/initialize.py` 负责建表 + 灌入角色、字典、菜单等（`sql/data/` 下是 JSON 种子）。你至少要先灌：
- 一个**管理员角色** + 一个**管理员账号**（否则系统进不去）
- 字典表（性别、证件类型等枚举）

## 第 6 章 · 写第一个业务模块（最关键，2~3 天）

**别 12 个模块一起写**。先挑最核心的一个打通。本项目选的是「医生端建档→填报→提交」。

本项目一个模块的**标准三件套**（都在 `backend/app/plugin/module_cpx/doctor/` 下，已实测存在）：

| 文件 | 职责 | 怎么写 |
|---|---|---|
| `controller.py` | 路由 + 入参校验（"接单窗口"） | 定义 `APIRouter`，用装饰器声明接口 |
| `service.py` | 真正业务逻辑（"做菜"） | 连数据库、算结果、调 AI |
| `schema.py` | 请求/响应数据结构（"订单格式"） | Pydantic 类 |

### 6.1 controller.py（真实写法）

本项目 `doctor/controller.py` 头部（已实测）：

```python
from fastapi import APIRouter
from app.plugin.module_cpx.doctor.schema import CaseCreateSchema
from app.plugin.module_cpx.doctor.service import DoctorService

DoctorRouter = APIRouter(prefix="/doctor", tags=["医生端"])   # 本模块前缀 /doctor

@DoctorRouter.post("/case/create", summary="患者快速建档（生成病例编号）")
async def case_create(data: CaseCreateSchema, ...):
    return SuccessResponse(await DoctorService.create(data))
```

> 你照做：新建 `controller.py` → 定义 `XxxRouter = APIRouter(prefix="/xxx")` → 用 `@XxxRouter.get/post/put(...)` 写接口。**函数体只做"收参数 + 调 service + 返回"，别把逻辑写这里。**

### 6.2 schema.py（真实写法）

本项目 `doctor/schema.py` 里的建档结构（已实测）：

```python
from pydantic import BaseModel, Field

class CaseCreateSchema(BaseModel):
    patient_name: str = Field(..., min_length=1, max_length=50, description="患者姓名")
    gender: str | None = Field(default=None, max_length=10, description="性别")
    age: int | None = Field(default=None, ge=0, le=200, description="年龄")
    phone: str | None = Field(default=None, max_length=20, description="联系电话")
    template_id: int = Field(..., description="填报模板ID")
    # ... 其他字段
```

> `Field(..., ...)` 里的 `...` 表示**必填**；`default=None` 表示选填。`description` 会显示在 Swagger 文档里。

### 6.3 service.py（真实写法）

本项目 `doctor/service.py` 三个核心函数（已实测函数签名）：

```python
class DoctorService:
    async def create(self, data) -> dict:          # 建档：生成病例编号，建草稿
        ...
    async def save_form(self, *, id: int, template_id: int, form_data: dict) -> dict:  # 保存填报
        ...
    async def submit(self, *, id: int) -> dict:     # 提交审核：状态→待审
        ...
```

`create()` 里真实在干的事（节选，已实测）：先查模板是否存在且已发布 → 解析日期字段 → 生成病例编号 `case_no` → 新建 `CaseRecordModel` 一行存进库。这就是"接单→做菜→入账"的完整动作。

> 你照做：`service.py` 里写所有业务逻辑；`controller` 只负责"调它"。这样以后逻辑改了不动路由，分工清楚。

## 第 9 章 · 尽早定下"核心抽象"（决定后期成本）

本项目最值钱、也最该早做的设计：

### 9.1 字段字典驱动表单（强烈建议）

`backend/app/plugin/module_cpx/fields.py` 一处定义 **67 个标准字段**（`field_code -> {name, type, tab, options, required}`），Web 表单、App 表单、填报模板都从它生成。

```python
# fields.py 真实结构（节选）
DIAGNOSE_TYPES = [{"label": "STEMI", "value": "STEMI"}, ...]   # 诊断类型选项
COME_TYPES = [{"label": "120 急救", "value": "120"}, ...]       # 来院方式选项
# 字段字典：field_code -> {name, type, tab, options, required}
```

> 你做自己项目：凡是"表单字段会随业务变"的场景，都用这套——改一个字段，两端同步，不用各改各的。本项目早期没做全，老病例只存了 6 个字段、数据丢了，教训深刻。

### 9.2 动态路由插件机制（见第 3.2 节）

加业务模块零注册，团队大了也不会漏挂路由。

## 附录：一条请求的真实生命周期（张三来就诊）

```
1. App(5190) 医生点"建档" → 发 POST /cpx/doctor/case/create
2. 后端(8002) 路由接到 → controller 校验参数 → 调 DoctorService.create()
3. service：查模板 → 生成 case_no → 往 case_record 表插一行（patient_name=张三）
4. 返回 {case_no: "...", id: 101}
5. 医生填表 → POST /cpx/doctor/case/{id}/save → service 往 case_detail 插一行
6. 医生提交 → POST /cpx/doctor/case/{id}/submit → 状态变"待审"，往 audit_record 插一行
7. Web(5180) 审核员看到这条待审 → 审核 → 往 audit_record 再插一行（结果）
```

看懂这条线，你就看懂了整个系统是怎么转的。
